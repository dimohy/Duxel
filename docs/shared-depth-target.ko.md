# 그래픽 큐의 깊이 버퍼 공유

2026-11-06. 공통 Vulkan 엔진은 매 렌더링에서 초기화하는 깊이 버퍼를 스왑체인 이미지별로 복제하지 않고 하나만 보유한다. 깊이는 표시하거나 다음 프레임의 내용으로 재사용하지 않는다. MSAA, 깊이 비교, 알파/coverage, 스코프별 초기화와 그리기 내용은 유지한다.

각 렌더링 전 EARLY_FRAGMENT_TESTS와 LATE_FRAGMENT_TESTS의 읽기·쓰기를 다음 깊이 초기화/검사보다 먼저 끝내도록 이미지 배리어를 설정한다. 이전 내용은 UNDEFINED로 버리고 CLEAR로 시작한다. 크기 변경 시 기존 자원은 마지막 그래픽 제출의 펜스가 완료된 뒤 해제한다. 이는 같은 그래픽 큐의 접근에 대한 계약이다. [Khronos 동기화 예제](https://docs.vulkan.org/guide/latest/synchronization_examples.html)를 대조했다. 새 CPU 대기나 QueueWaitIdle은 추가하지 않았다.

## 실제 진단과 비교

근거는 `artifacts/gpu-current-2026-11-06/`이다. SDK11.0.100-rc.3.26522.148/runtime11.0.0-rc.3.26522.148, win-x64 NativeAOT Speed를 고정했다. GPU 입자5,000개·크기6·충돌2회·VSync 끔·MSAA4·파이프라인/정적 캐시/동적 캔버스 켬, 요청1920×1080, 현재 DPI의 실제2400×1350이다. 부하와 품질을 줄이지 않았다.

기존 측정기로 독립3회씩 A/B, B/A, A/B 순서로 실행했다. 워밍업1초, 측정6초. 성능 비교 전 빌드와 기능 검사를 끝냈다. 강제 GC는 없다. Private/작업 집합은 프로세스 시작3~6초 표본의 실행별 중앙값을 다시 세 실행으로 집계했으며 UI 워밍업 시점과 정확히 일치하는 표본이 아니다.

GPU 타임스탬프는 입자 compute부터 렌더링까지 포함하며 CPU/표시 완료 시간을 의미하지 않는다. 별도57개 단계 표본의 imageFence 중앙값366.8μs, 명령 기록31.9μs였다. 이 장면에서 draw 수 자체가 수천 번은 아니며 GPU/이미지 재사용 대기가 컸다. 깊이 할당과 프로세스 Private는 다른 계층의 값이다. Private 감소를 GPU VRAM 전체 감소로 바꾸어 해석하지 않는다.

수정 전30초 관측에서는 초기 상승 뒤 Private가 비슷한 범위였다. 장기 누수 해결·피크 상한·전체 위젯 성능·Pi 실측을 입증하지 않는다. 공유로 프레임 사이 깊이 작업의 병렬성이 줄 수 있으므로 다른 GPU/장면 검증은 남는다.

## 측정기와 검증

`scripts/measure-polygon-performance.ps1`은 `Width`/`Height` 요청과 1초 간격 Private/작업 집합/CPU/핸들/스레드 CSV를 남긴다. 시작 전 케이스와 기존 출력 경로를 검사하며 덮어쓰지 않는다. 숨긴 창의 MainWindowHandle 부재는 실패 조건이 아니다. 프로세스 종료·raw 프레임 통계·GPU 지표로 실행을 확인하고, 화면 확인/수동 입력 승인은 별도로 남긴다. 최초 실행의 잘못된 핸들 판정과 원본 자료는 보존했다.

.NET10 전체 렌더링1,862개, 추가 변경 깊이 큐 검증 포함1,067개를 확인했다. 큐 검사는 MSAA1/4에서 readback 없이12프레임씩 교대로 제출한 뒤 전체 픽셀·깊이 초기화·단일 할당을 확인한다. 최종 Native 및 이미지 대조 결과는 같은 폴더의 `verification.json`을 따른다. 과거 이미지320×240와 현재400×300을 직접 동치 비교하지 않는다. 기존 실행 파일을 현재 DPI에서 재사용하고 새 검사를 기존 스냅샷 뒤에 실행해 UI 이력을 분리한다. 허용 오차나 이미지 크기 조절로 차이를 숨기지 않는다.
