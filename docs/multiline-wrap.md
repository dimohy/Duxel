# Wrapped multiline layout

Set `UiMultilineInputLayout.Wrap = true` in a compiled multiline presentation to wrap without adding newline characters to the bound model. The default remains `false` for existing raw multiline behavior. `layout_multiline_wrap_fba.cs` shows a generated custom presentation and a live editor whose allocation and content change.

Each wrapped editor lazily owns its visual rows, original UTF16 boundaries and advances. Rows break at fitting whitespace, or at a .NET `StringInfo` text-element boundary when a word does not fit. Empty hard lines and trailing newlines remain represented. An element wider than the available width stays whole and is clipped. Vertical overflow reserves the actual scrollbar gutter and reflows; wrapped mode does not create a horizontal scrollbar.

Painting, pointer hits, caret placement, selection, Home/End, Up/Down, Page keys and held-key repeat use these rows. End and pointer hits retain trailing affinity where adjacent visual rows share one model index. Consecutive vertical movement retains preferred X across shorter rows. Left/Right, deletion and selection alignment use text-element boundaries. Undo and binding notifications contain real edits only. This does not establish complete browser word-breaking, ligature, bidirectional or input-method conformance.

Text, allocation, gutter, line height and text-resource keys invalidate row data. Glyph observation that disables measurement retention also disables cross-frame row reuse; the prepared rows remain consistent within a render. Context transfer and disposal release cached strings and geometry. Wrap changes invalidate the mode; [readonly/Fluent nonwrapping geometry](multiline-hard-lines.md) continues to own hard rows, while the standard unwrapped editable path releases optional line data. Paint rejects a stale result after its owned mapping changes. IME preview has separate display rows, underlines and caret scrolling; queued-handler tests do not prove actual Windows IME interaction.
