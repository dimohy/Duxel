## PaintGroup 캡처 버퍼 소유권

가로로 넘치는 SegmentedControl의 선택 애니메이션은 이전 결과를 다시 만들면서 이미 분리된 그리기 버퍼를 한 번 더 복사했다. 내부 PaintGroup 캡처는 소유 버퍼를 스냅샷으로 이전한다. 공개 생성자와 빌린 버퍼의 복사 계약은 유지한다.

Linux x64 .NET 11 NativeAOT에서 동일 36개 위젯과 3·16프레임 주기의 선택을 변경 전후 각 6회 실행했다. 정상 애니메이션은 44,603.07→42,623.07 B/프레임(4.44% 감소), 모션 줄이기는 10,587.24→10,127.04 B/프레임(4.35% 감소)이었다. 선택 고정의 할당과 각 조건의 그리기 해시·재생성 횟수는 일치했다. Windows 수명·입력·Vulkan 검사 194개가 통과했다. 이 검증에서 GPU 시간과 절대 앱 FPS는 비교하지 않았다. [비교 및 검사 기록](L:/Cache/Duxel/linux-segmented-capture-20261120/comparison.json)

## SVG 레이어와 스크롤

갤러리를 띄워 둔 상태에서 실행 파일과 DLL을 확인했다. 실행 중인 11월 19일 빌드의 `Duxel.App.dll`에는 이벤트 대기 시간을 FPS 계산에서 제외하는 코드가 없었다. 동일한 화면을 테스트 창에서 재현하니 대기 시간 약 2.5초를 포함했을 때 `0.4 FPS · 2509.46ms`가 나왔다. 해당 프레임의 UI 구성과 Vulkan 제출에는 14.63ms가 걸렸다.

갤러리가 생성될 때부터 시간을 재면 첫 표시용 프레임을 그리기 전의 준비 시간도 FPS에 들어갈 수 있다. FPS 시계를 첫 표시용 프레임에서 시작하도록 바꿨다. 기존 이벤트 대기 시간 제외를 유지하고 새로운 렌더링 캐시를 추가하지 않았다.

.NET SDK 11.0.100과 관리형 런타임 11.0.0으로 확인했다. 테스트는 550ms 준비 지연 뒤 첫 프레임에서 `FPS 측정 중`을 유지하는지 확인한다. 1280×900, MSAA 4×의 테스트 창에 Win32 이벤트를 보내 스크롤바를 문서 전체 범위의 20% 이상 왕복하고 코드 선택을 확인했다. 64개 이동을 받은 스크롤바는 UI 배치 1회, 코드 선택은 2회로 처리했다. 첫 큰 이동에서 SVG 요청 1건과 프레임 47.98ms를 관측했다. 이후 왕복은 최대 6.32ms, 코드 선택 12회는 최대 8.08ms였고 SVG 요청은 0건이었다. 시간은 UI 구성과 Vulkan 호출이 반환되기까지의 합이다.

검증 명령은 `dotnet build Duxel.slnx -c Release`, `Duxel.Graphics.Tests <출력 폴더> gallery-svg-layer-mix`, `gallery-svg-code-scroll`, `ordered-input-batch-only`, `Duxel.Gallery --verify <출력 폴더>`다. 솔루션 빌드는 경고·오류 없이 완료했다. 순서 있는 입력 검사 597개와 갤러리 표시 시나리오 105개가 통과했다. 단일 관리형 진단이므로 처리량 개선율, 실시간 바탕 화면 지연 및 NativeAOT 동등성을 산정하지 않았다. ## Vulkan PaintGroup 이미지 재사용

PaintGroup의 크기가 그대로여도 그림 스냅샷이 바뀔 때마다 합성용 이미지를 다시 할당했다. 출력 ID와 픽셀 크기가 같은 갱신에서는 합성용 이미지 두 장과 MSAA용 이미지의 소유권을 유지하고 스냅샷만 교체한다. Vulkan 배리어는 직전 합성의 읽기와 이미지 쓰기가 끝난 뒤 다시 그리도록 한다. 이미지 크기나 렌더링 형식·샘플 수가 바뀌면 기존 지연 해제 경로를 사용한다.

## Windows ERD 상태줄의 글리프 재사용

실제 ERD가 요청한 글자 크기는 18.24픽셀이었다. 기존 글리프 경로에는 정확히 16픽셀만 전달돼 실제 창의 초기 대조 6회에서 활성화되지 않았다. 요청을 기존 DirectWrite 경로와 같은 18픽셀로 반올림하고 글자 크기를 글리프 캐시 키에 넣은 후보를 격리해 비교했다.
