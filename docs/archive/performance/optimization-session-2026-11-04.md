## 공통 위젯 최적화 평가 후 추가 개선

가설: 기본 위젯에 부분 갱신이 적용됐어도, 변경 판정이 기하 업로드 뒤에 실행되면 draw0인 프레임의 메모리 대역폭·CPU 작업은 남는다. 실제 일반 위젯5종에서2776~10320B/frame, 고부하 팔레트에서57632B/frame 업로드를 확인했다.

변경: 공통 Vulkan 경로에서 획득 이미지 변경 판정을 streamed 업로드·용량 확장 앞에 배치하고 빈 변경 영역의 업로드·파이프라인 bind·compiled 계획·draw 순회를 생략했다. 입력·레이아웃·정적 캐시·texture 무효화·프레임 제출은 유지한다. 첫 후보의 정지 FPS-2.06%를 보존하고, 공통 rectangle/circle/rounded primitive의 현재 명령을 ref로 처리하여 값 복사 경로를 줄였다. 샘플·부하·셰이더·벡터 품질은 바꾸지 않았다.

검증: .NET10.0.9 및 고정 RC3 각각717회귀·70위젯/scroll/resize검사 통과, 갱신 주기 비동기 검사386개 통과, 이전 이미지317개 동치. 솔루션 net8/9/10 Release 경고0·오류0. 기존 검사·측정기·원본 데이터를 재사용했다.

판정·리스크: Windows 공통 경로의 방향과 추가 개선은 확인했지만 임의 UI Render 전체의 CPU 생략과 라즈베리파이 실기기 성능은 증명하지 않았다. 표본 GC 진단은 전체 앱 GC없음의 증거가 아니다. 메모리·CPU·GPU·업로드를 구분하고 기존 단계의 Private 감소율과 합산하지 않는다. [평가·명령·정확한 비교표](../../optimization-evaluation.ko.md), 원본 `artifacts/optimization-evaluation-2026-11-04/` 참조.

## 종합 샘플 FPS 깜빡임 교정

가설: 버튼 유지·3000 FPS 이상에서 FPS 줄만 소실되는 것은 부분 갱신 또는 느린 갱신과 빠른 갱신 사이의 공통 캐시 전환 문제다. 전체 갱신·관리 실행에서도 재현되어 부분 갱신과 NativeAOT만의 원인은 제외했다. 매 프레임 두 줄을 변경하는 1024프레임 검사로는 재현되지 않았고, FPS는16프레임·NF는3프레임 유지하는 128프레임 검사에서 비동기 프레임1의 이전 내용 표시를 재현했다.

변경: `UiRetainedLayerBatcher`의 기하 기반 캐시 키에 명령 상태 지문을 추가했다. 같은 기하라도 텍스처·클립·불투명도·오프셋 변경 시 배치를 재구성한다. 캐시·부분 갱신·부하·벡터 품질을 유지한다. `UiFpsCounter`의 밀리초 프레임 누락을 고해상도 시간으로 교정했다. 별도 정확성 수정으로 swapchain clipping과 이미지별 present semaphore 수명도 보완했으나, 이 둘만으로 사용자 증상은 해결되지 않았다.

검증: SDK10.0.301/.NET10.0.9에서 `dotnet run --project tests/Duxel.Rendering.Tests -c Release -- artifacts/all-features-2026-11-04/regression-complete-fixed` 715개 통과. `--all-features-overlay-only`로 128개 동기·128개 비동기 프레임의 검사386개 통과. 사용자가 최종 NativeAOT 창에서 버튼 유지 시 깜빡임 소멸을 확인했다. 37개 창·6개 상호작용도 통과했다. 명령 인수와 근거는 [종합 샘플 검증](../../all-features-validation.ko.md), 원본은 `artifacts/all-features-2026-11-04/`에 있다.

Before/After: 동일 검사에서 비동기 프레임1 불일치 → 128프레임 전부 전체 갱신 기준과 일치. FPS 계산은 고속 프레임 누락 → 모든 호출 계산(10000회 집중 검사). 성능 개선율·메모리 개선율·median/p95/p99·1% low는 이번 정확성 교정에서 측정하지 않았으며 추정하지 않는다. 단일 진단 프로필을 3회 중앙값 벤치로 간주하지 않는다. 기존 고정 .NET11 RC3 Speed 성능 근거는 보존하며 이번 .NET10 기능 검증과 합산하지 않는다. 리스크: NativeAOT 게시의 ILCompiler NU1903 경고는 남았다. 보호 출력·기존 미커밋 변경을 보존했다.

가설: 기존 GPU 모드는 도형 수 변경 시 `UiGpuParticleSystem`을 폐기하고 CPU의 초기 seed로 다시 생성하므로 모든 도형이 초기화된다. 체크박스는 UI 값뿐 아니라 실제 레이어·캐시·swapchain·MSAA 상태까지 확인해야 한다.

공통 변경: 불변 `UiGpuParticleSnapshot`과 도형별 생성 ID를 도입하고, `Append`/`Truncate`로 살아 있는 prefix를 보존한다. 프레임 생성 시 스냅샷을 고정하여 대기 중인 프레임의 개수가 바뀌지 않는다. GPU 용량 안에서는 새 seed만 전송하고, 확장 시 기존 GPU 상태를 장치 내부에서 복사한다. 그래픽 큐의 transfer/compute 의존성과 기존 프레임의 자원 수명을 유지한다. CPU 기준 모듈도 같은 편집 계약을 사용한다.

컨트롤: NativeAOT 검증 창에 실제 Win32 메시지를 보내 Dynamic Canvas Layer, VSync, Global Static Cache, Render Profile을 왕복 전환했다. 레이어 push, 배경 residency, 실제 표시 모드, 실제 MSAA와 UI 상태를 비교했다. Add/Remove/Reset/Clear도 포함한24검사가 통과했다. VSync ON은 FIFO로 바꿨고, 실제 적용 설정을 `UiRendererFrameMetrics`에 노출했다. 입력 검증기는 누르기와 떼기 양쪽에 마우스 위치를 전달하며 전역 커서를 이동하지 않는다.

정확성: 추가·확장·삭제 후 기존48바이트 상태 전체 일치, 같은 개수로 삭제/재추가한 경우의 생성 ID, 대기 프레임, 이동 재개 및 CPU 기준을 검사했다. 추가100개의 상태 전송은4800B이며 기존5000개를 재초기화하지 않는다. Clear/Reset만 명시적으로 새 시스템을 만든다.

## 메뉴·팝업 공통 표시 레이어 — 최종 결과

목표: 메뉴·컨텍스트 메뉴·툴팁·전경 그리기를 공통 동적 레이어 경로로 통합하고, 중간 성능 하락을 원인 개선으로 해결한다. 기존 샘플을 수정하는 대신 `overlay_layer_lab.cs`를 추가했다. 별도 오프스크린 합성 텍스처 없이 기존 벡터/명령과 화면 고정 평면을 사용한다.

변경: 분산된 전경/팝업 빌더와 매 프레임 병합 배열을 `UiPresentationLayers`로 통합했다. 범위별 기하·명령을 정확히 비교해 불변 스냅샷을 재사용하고 대기 프레임의 마지막 독자가 끝난 뒤 버퍼를 회수한다. 움직이는 표면은 공통 동적 업로드를 쓰고 안정되면 상주 버퍼로 돌아간다. 화면과 일치하는 평면은 불필요한 변환·깊이 이미지·별도 파이프라인을 생략한다. 이 경로는 내부 `IsScreenSpacePresentation` 표시를 확인하며 일반 3D 장면의 깊이 검사는 보존한다. 팝업 입력 겹침 계산은 프레임당 한 번 공유하고, 중첩 ID/팝업 키는 제한된 컨텍스트 캐시를 사용한다. 작은 버퍼의 초기 용량과 유지 배처의 임시 메모리를 줄였으며, 화면 표시 사각형의 불필요한 삼각형 확장을 피한다.

중간 하락/실패와 수정: 깊이 쓰기는 반투명도·AA를 바꿔 순서가 정해진 평면에 깊이를 쓰지 않도록 했다. 일반 3D 텍스트까지 단순화하면 ClearType 경로가 달라져 화면 표시 평면으로 범위를 제한했다. 숫자 범위 ID만으로 최적화한 경로는 사용자 `int.MinValue` 깊이 검사 재현에서 실패했으며, 엔진 전용 표시를 추가한 뒤 같은 검사를 통과했다. 계속 움직이는 팝업을 매번 GPU 상주 버퍼로 바꿀 때의 비용은 동적 스트림으로 해결했다. UI 스레드의 프로세스 메모리 조회는 프레임 지연을 유발해 별도 작업으로 옮겼다. 최소화 크기 160×28 관측 및 불완전 측정은 거부했다. 회귀가 생겼다는 이유로 레이어 통합을 폐기하지 않았다.
