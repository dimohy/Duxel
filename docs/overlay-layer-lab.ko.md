# 메뉴·팝업 동적 레이어 실험실

최신 공통 엔진 후속은 [변경 영역 렌더링](retained-rendering.ko.md)을 우선한다. 아래40C51851과 이전 수치는 해당 단계의 역사적 결과다.

`samples/fba/overlay_layer_lab.cs`는 공통 엔진 경로를 확인하는 전용 샘플이다. 기본 부하는 팝업 48개, 팝업당 항목 5개·벡터 색상 견본 64개와 배경 도형 1,800개다. 화면에는 같은 위치에 여러 팝업이 겹치도록 배치한다. `Animate one palette`는 첫 팝업만 움직이며, 오른쪽 클릭 메뉴에는 하위 메뉴가 있다. 툴팁은 포인터를 따라 움직인다.

```powershell
./run-fba.ps1 samples/fba/overlay_layer_lab.cs -NoCache
```

공통 엔진은 기존 `BeginPopup`, 컨텍스트 메뉴, `BeginMenu`, 콤보, 툴팁과 전경 그리기 API를 자동 표시 레이어로 처리한다. 샘플이 별도 캐시를 만들거나 위젯의 입력 처리를 생략하지 않는다. 입력·레이아웃은 매 UI 프레임 실행하고, 만들어진 기하와 명령이 같으면 불변 스냅샷을 그대로 사용한다. 비교는 해시만이 아니라 실제 버퍼 내용으로 한다. 팝업 하나가 바뀌면 해당 팝업의 스냅샷만 교체한다.

화면 고정 레이어는 3D 변환과 깊이 범위를 가지며, 표시 순서는 전경 → 팝업 깊이 순서다. 같은 깊이에서는 제출 순서를 유지한다. 순서가 이미 결정된 화면 고정 평면은 깊이 쓰기와 별도 깊이 이미지를 사용하지 않는다. 기존 알파 블렌딩과 하드웨어 scissor를 적용해 반투명도, 글자 가장자리와 클리핑을 유지한다. 화면 좌표와 정확히 일치하고 깊이 쓰기가 없는 평면은 결과에 영향을 주지 않는 변환을 생략해 기존 그래픽 파이프라인을 공유한다. 일반 카메라·3D 장면의 깊이 검사 경로는 유지한다. `UiLayer3D.PresentationDepthScopeId`는 엔진 표시 레이어용 예약 값이다.

새 API:

```csharp
ui.SetNextPopupPosition(new UiVector2(100, 150));
if (ui.BeginPopup("properties"))
{
    ui.MenuItem("Inspect");
    ui.EndPopup();
}
var counters = ui.GetOverlayLayerMetrics(); // Current UI frame, completed scopes.
// counters.ReusedLists / counters.RebuiltLists
```

`SetNextPopupPosition`은 다음 `BeginPopup`에만 적용하며 좌표는 화면 기준이다. 카메라 확대를 상속하지 않는다. 팝업을 여는 동작은 기존 `OpenPopup`을 사용한다. 위치나 내용이 바뀌면 해당 팝업의 기하를 다시 생성한다. 임의 위젯의 입력 처리까지 건너뛰거나 모든 이동을 행렬 변경만으로 처리하는 API는 아니다.

이전 프레임이 렌더 큐에서 데이터를 사용하는 동안에는 교체된 버퍼를 반환하지 않는다. 팝업이 닫히거나 컨텍스트가 폐기되면 더 이상 참조되지 않는 스냅샷을 회수한다. 콜백과 실행 상태가 있는 명령은 프레임별 실행 경로를 사용한다.

## 측정

`DUXEL_OVERLAY_COUNT`는 1~512, `DUXEL_OVERLAY_SWATCHES`는 팝업당 색상 견본 0~512개, `DUXEL_OVERLAY_SCENARIO`는 `idle` 또는 `motion`이다. `DUXEL_OVERLAY_OUT`과 `DUXEL_OVERLAY_SECONDS`를 지정하면 최소 96프레임·1초 준비 후 측정하고 종료한다. 측정 샘플은 렌더링 처리량 비교를 위해 유휴 프레임 생략을 끈다. 이는 일반 앱의 기본 설정을 바꾸지 않는다. 팝업을 계속 열어 두므로 외부 클릭으로 비교 부하가 줄어들지 않는다.

`scripts/measure-overlay-layers.ps1`은 같은 샘플로 만든 이전/이후 실행 파일을 교대로 실행한다. 최소 3회 반복하고, 실제 표시 제출 이력의 원본 프레임 시간, 실행 파일·관리 어셈블리 해시, 독립 stdout/stderr와 결과를 저장한다. FPS는 모니터 주사율이 아닌 성공한 표시 제출 처리량이다. 실제 프레임버퍼 크기가 바뀌거나 요청한 측정 시간을 채우지 못하면 실패 처리하며, 렌더 스레드 오류가 있는 결과도 비교에서 제외한다. 메모리는 창이 열려 있는 측정 구간에 250ms마다 수집한 private/working set의 중앙값으로 기록한다. 종료 후 메모리를 실행 중 메모리로 해석하지 않는다.

CPU 전용 비교는 `tests/Duxel.Performance.Bench`의 `--overlays` 옵션이다. GPU·표시 시간을 포함하지 않는다. 프레임당 할당, GC 후 관리 메모리, 프로세스 private bytes는 서로 다른 지표다. 관리 메모리 검사는 시간 측정 루프 밖에서 실행한다.

실측과 중간 성능 하락 기록은 [2026-11-04 최적화 기록](archive/performance/optimization-session-2026-11-04.md)을 참고한다. 픽셀·수명 검사는 `OverlayPresentationTests`에서 실행한다.

팝업 겹침 검사는 이전 프레임의 고정된 사각형 목록과 현재 마우스 위치를 프레임당 한 번 계산해 모든 위젯이 공유한다. 기존의 팝업 수×위젯 수 반복을 팝업 수+위젯 수로 줄이며, 높은 팝업이 아래 위젯의 입력을 차단하는 규칙을 유지한다. 계속 바뀌는 팝업은 공통 동적 전송 버퍼를 사용해 매번 GPU 상주 버퍼를 할당하지 않고, 다시 안정되면 상주 재사용으로 돌아간다.

최적화 적용에는 엔진이 설정한 `UiLayer3D.IsScreenSpacePresentation` 표시도 필요하다. 사용자 장면의 깊이 범위 ID가 `PresentationDepthScopeId`와 같더라도 일반 깊이 검사를 유지한다. 범위 ID 숫자만으로 렌더링 동작을 바꾸지 않는다.

중첩 위젯 ID와 팝업 상태 키는 컨텍스트별 제한된 문자열 캐시를 공유한다. 최대 4,096개·계산된 문자열 길이 1,048,576자이며 오래 쓰지 않은 키는 회수한다. 작은 기하 버퍼의 초기 용량을 줄이고, 표시 레이어의 사각형은 전송량이 늘어나는 삼각형 확장을 피한다. 샘플에서만 적용되는 설정이 아니다.

비교 창은 기본적으로 숨겨 실행해 크기 변경의 영향을 줄인다. 화면을 보며 비교하려면 `-VisibleWindow`를 지정한다. 메모리 관측은 UI 밖의 작업에서 수행한다. `-SummarizeOnly -OutDir <결과 폴더>`는 바이너리를 다시 실행하지 않고 원본 프레임과 요약을 대조한다.

```powershell
$measure = @{
    BeforeExecutable = '<동일 샘플의 이전 실행 파일>'
    AfterExecutable = './samples/fba/artifacts/overlay_layer_lab/net11.0-windows7.0/overlay_layer_lab.exe'
    OutDir = './artifacts/overlay-comparison'
    Counts = @(128); Swatches = 256
    Scenarios = @('idle', 'motion'); Runs = 3; Seconds = 3
}
./scripts/measure-overlay-layers.ps1 @measure
```

## 2026-11-04 엔진 수정 완료 시점의 결과

.NET 11 NativeAOT Speed, 1600×1000, VSync off, MSAA1, 준비 최소 1초·96프레임 후 3초씩 이전/이후 각 3회 교대 측정했다. 실행별 평균 FPS의 중앙값이다.

아래 표와 `7B1A3575`는 이전 단계의 결과다. 현재 배포 파일은 `40C51851`이며, 뒤의 추가 메모리 최적화 결과를 함께 확인한다.

| 팝업/견본 | 상태 | 이전 FPS | 이후 FPS | 변화 |
| --- | --- | ---: | ---: | ---: |
| 48/64 | 정지 | 2007.95 | 2023.03 | +0.75% |
| 48/64 | 하나 이동 | 1970.11 | 2004.83 | +1.76% |
| 128/256 | 정지 | 359.30 | 387.50 | +7.85% |
| 128/256 | 하나 이동 | 361.48 | 382.84 | +5.91% |

작업 집합은 모든 조건에서 약 9.6~12.9MiB 감소했다. 기본 부하의 Private도 감소했지만 128/256에서는 약 12.3~14.4MiB 증가했다. 큰 부하의 UI Render 본문 할당은 72,720→정지 0/이동 608B, 동적 전송은 약 94~95% 감소했다. draw calls는 그대로다. CPU 전용 32단계 검사는 프레임 할당 16,152→264B, GC 후 유지 관리 메모리 약 10.18→0.61MiB를 기록했다. 전체 프레임 할당이나 GPU 표시 FPS와 혼동하지 않는다.

.NET 10·11 각각 507개 검사, 이전 GPU 이미지 142개 동치, Release 빌드 경고·오류 0개를 확인했다. 원본 기록과 한계는 위 최적화 기록을 따른다. 샘플의 처리량은 모니터 주사율과 다르며 모든 장치·장시간 동작의 성능을 의미하지 않는다.

이후 시연 툴팁이 컨텍스트 메뉴를 가리지 않도록 수정한 당시 배포 파일(`7B1A3575`)도 같은 조건으로 재측정했다. 기본 48개에서는 정지 1901.21→2007.09FPS, 이동 1961.84→1962.87FPS지만 범위가 겹쳐 개선을 확정하지 않는다. 128개에서는 정지 365.05→380.03FPS(+4.10%), 이동 375.58→382.72FPS(+1.90%)로 범위가 겹치지 않았다. 작업 집합은 약 9.6~13.2MiB 감소했고, 큰 부하 Private는 약 10.1~14.9MiB 증가했다. `native-ui-final-{default,stress}`가 해당 배포 파일의 근거다. 기본 정지의 이전 실행 한 번은 578.34FPS였으며 원인 미확정 상태로 원본에 그대로 포함했다. 최신 이동 부하의 1%low 개선은 확인하지 못했다.

## 추가 메모리 최적화 — 현재 배포 40C51851

공통 배처는 기하 소유권을 넘긴 뒤 곧바로 비울 작업 버퍼를 큰 크기로 다시 빌리지 않는다. 일시적인 배처만 작은 대체 버퍼를 유지하고 일반 프레임 빌더는 기존 용량을 유지한다. 다른 샘플에도 적용되는 코어 변경이다.

직전 배포 7B1A3575와 128개 팝업·견본256개를 같은 설정으로 각3회 교대 측정했다. Private 중앙값은 정지197.94→196.09MiB(-1.84MiB), 하나 이동200.95→197.63MiB(-3.32MiB)로 실행 범위가 겹치지 않았다. FPS는 정지380.90→394.97, 이동382.40→393.96이지만 범위가 겹쳐 이 추가 수정의 성능 향상을 확정하지 않는다. 큰 부하 Private가 처음 구현보다 높다는 한계는 남아 있다. 이 단계 근거는 `scratch-memory-comparison/summary.json`과 `scratch-memory-results.json`이다.

.NET10·11 각각510개 검사, 직전 이미지155개 동치와 Release 경고·오류0개를 확인했다. 현재 EXE SHA256은 `40C51851C9469653BA40DBCD9B8FE36ABD2D3411538E1A5FC8090AB4DD786B92`다. 삭제가 거부된 임시 산출물은 직접 정리 안내에 대상과 방법을 남겼으며, 실제 삭제는 수행하지 않았다.

현재40C51851과 최초 기준 실행 파일을 다시 직접 비교한 최종128개 부하 결과도 보존했다(`completion-native-original/summary.json`). 정지366.35→374.07FPS(+2.11%), 이동363.44→381.36FPS(+4.93%)로 실행 범위가 겹치지 않았다. 작업 집합은 정지135.71→122.69MiB, 이동135.79→123.42MiB로 감소했다. Private 중앙값은 정지185.93→196.02MiB, 이동186.67→198.04MiB여서 모든 메모리 지표가 처음보다 낮은 것은 아니다. 최종 원본에는 p95·p99·느린1%와 각 실행 범위도 함께 보존했다.
