# Tooltip surface and qualification

Last synced: 2026-11-11

`UiFluentTooltipPresentation` and `UiFluentInvertedTooltipPresentation` opt a real `UiTooltip<TBehavior, TPresentation>` owner into the Fluent surface and Type200 text. The custom-container sample uses the default presentation through its compiled offset policy. `Arrange<TOffset>` preserves that extension point. There is no new `Fluent.Tooltip` factory or catalog entry; the complete control remains unfinished.

The border box has maximum width240, radius4, a transparent1-unit border and CSS padding4/11/6/11. Text therefore begins12 units from the left and5 from the top, with7 below. Actual wrapping is remeasured at the resolved width; visible and full content extents remain separate, and painting applies the owner's scroll offset and root clip. Positioning with an arrow requires height6 and square edge8.484; another explicit height/edge fails. The rounded arrow includes the square and its triangular, border-expanded pseudo-element. Its facing-axis center lies1 unit inside the body edge. Positioning still uses the shared collision/offset/auto-size lifecycle.

Default Light colors are background255/foreground36; default Dark colors are background41/foreground255. Inverted backgrounds are51 in Light and61 in Dark, with foreground255. The pinned [Fluent styles](https://github.com/microsoft/fluentui/blob/8830c10bfb2f4c1bdd540287b09713b9679cd1ad/packages/react-components/react-tooltip/library/src/components/Tooltip/useTooltipStyles.styles.ts) supply these surface rules and tokens. The combined body/arrow alpha first receives black ambient shadow with standard deviation2 and opacity0.12/0.24, then black key shadow with deviation8, vertical offset4 and opacity0.14/0.28. The key shadow consumes the complete first result. This follows [Filter Effects](https://www.w3.org/TR/filter-effects-1/#funcdef-filter-drop-shadow), whose third length specifies standard deviation and whose filter list is sequential.

The implementation rasterizes one combined RGBA surface with8x8 coverage samples and separable Gaussian kernels truncated at four standard deviations. Physical content scale and fractional origin phase participate in the cache key. Each visible tooltip has a bounded slot that reuses unchanged shapes and integral translations, replaces changed shapes and retires the texture on owner release/omission/disposal. A second distinct shape for the same slot in one frame fails before destroying that frame's texture. Dimensions above4096 on either axis or above4,194,304 pixels fail explicitly. This is an explicit CPU raster path uploaded through the existing image pipeline; no alternate renderer or shader was added. Cold raster cost and full application performance are not measured.

Window-owned color texture IDs reserve1,000,000,002 through1,099,999,999, below the renderer's font-mask threshold. The icon uses1,000,000,001. Applications must not assign their own images in those reserved ranges. Exhaustion fails explicitly. Initially using the DirectText ID allocator made the renderer treat color as ClearType coverage; visual review caught the incorrect bright Dark surface. The corrected path has independent GPU byte checks for all four background colors and for shadows darkening the background.

Evidence lives in `artifacts/tooltip-surface-2026-11-11`: the fixed .NET11 RC3 build has zero warnings/errors, CPU4,045 and Tooltip GPU740 checks pass, and the consumer sample exits successfully after15 seconds/30 state transitions. GPU checks compare actual owner placement/text/padding against explicit literal scenes in Light/Dark and MSAA1/4, then check independent palette bytes and shadow direction. The same surface rasterizer is shared by the literal scenes: those comparisons do **not** establish CSS pixel fidelity.
