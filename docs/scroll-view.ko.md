# 소유 스크롤 뷰

갤러리의 **레이아웃과 입력 → 레이아웃 예제**를 열고 본문에서 **ScrollView**로 이동하세요. 세로와 가로·세로 스크롤을 바꿔 볼 수 있고, 바로 아래 C# 코드에도 선택한 축이 반영됩니다.

갤러리와 같은 Linux D-Bus·X11 세션에서 `dotnet Duxel.Linux.App.Tests.dll x11-gallery-scroll-view <갤러리-PID> <새-result.json> <10진수-X11-창-ID>`로 검사할 수 있습니다. AT-SPI로 C# 코드를 읽고 두 축의 X11 휠 이벤트를 보내 예제 안에서 항목이 움직이는지 확인합니다.

가로 휠을 좌우로 24번 반복해 계측하려면 같은 인수로 `x11-gallery-scroll-profile`을 실행하세요. 갤러리에 `DUXEL_APP_PROFILE=1`, `DUXEL_APP_PROFILE_EVERY=1`, `DUXEL_APP_PROFILE_OUT`을 설정하고 클라이언트에도 같은 로그 경로를 지정합니다. Vulkan 단계별 시간도 보려면 `DUXEL_VK_PROFILE=1`, `DUXEL_VK_PROFILE_EVERY=1`을 설정하고 두 프로세스에 같은 `DUXEL_VK_PROFILE_OUT`을 지정하세요. 클라이언트는 스크롤바가 멈출 때까지 각 로그에서 측정한 줄 범위를 출력합니다.

Vulkan 로그의 `[duxel-vk-wsi]` 줄에는 생성에 성공한 스왑체인의 V-Sync 설정, 지원 모드, 선택 모드, 이미지 수와 크기가 기록됩니다. WSLg의 lavapipe에서는 V-Sync가 꺼진 상태에서 `ImmediateKhr`이 선택됐고, ScrollView를 움직이는 동안 기록한 38개 프레임에서 CPU의 Present 호출 p95는 4.333ms였습니다.

2026-11-10 [키 가상 목록](virtual-list.ko.md): 세로 고정 높이 행을 double 오프셋·뷰포트 근처 좌표로 배치해 10억 항목을 처리합니다. CPU43·확대 좌표2317검사 통과, 범위 밖 행은 기존 소유권으로 해제합니다. 가변 높이/다른 축·교차 키 재활용 정책·외부 UIA·현재 Native는 미완료이며 컨테이너3/6 유지. 샘플: `layout_virtual_list_fba.cs`.

`Dux.ScrollView(child, options)`는 자식 `UiWidget` 하나, 콘텐츠 오프셋과 스크롤바 입력 수명을 소유하는 `UiScrollView`를 만듭니다. 기존 위젯 측정·월드 좌표 자식 배치·클립·휠·스크롤바 커널을 사용합니다. 새 Fluent 외형 컴포넌트가 아닌 레이아웃 인프라입니다.

```csharp
var editor = Fluent.Input("Editor", text.Binding, 256);
using var view = Dux.ScrollView(
    new UiColumn(
        [editor, .. rows],
        new(Spacing : 8, MainAxisSize : UiMainAxisSize.Min)),
    new(UiScrollAxis.Vertical, Width : 300, Height : 280));
view.Offset = new(0, 120);
view.AccessibleName = "Editor viewport";
```

`text`는 `UiState<string>`이며 `rows`에는 소유할 위젯 인스턴스가 들어갑니다. 자식을 다른 소유자와 공유할 수 없습니다. 뷰를 해제하면 하위 트리를 한 번 해제하고 스크롤바 캡처·보조 상태를 제거합니다. 실제 입력 자식도 기존 소유권 경로로 버퍼와 undo 이력을 해제합니다. 약한 컨텍스트 참조를 사용하므로 같은 스크롤 인스턴스를 다른 UI 컨텍스트에서 렌더하면 이전 컨텍스트의 스크롤바 상태를 정리합니다. 기본 인스턴스 정체성은 뷰마다 독립적이며, 부모 정체성에는 호출자의 정상적인 구별된 ID 스코프가 필요합니다.

## 제약과 콘텐츠

`UiScrollOptions`는 기본 `Vertical`, `Horizontal`, `Both`와 선택적 `Width`·`Height`를 지정합니다. 뷰포트의 두 축은 부모 제약이나 명시적 옵션으로 유한해야 합니다. 강제 부모 할당이 우선합니다. 높이 무제한 Column 안에서는 높이를 지정하거나 SizedBox로 감쌉니다. 유한 경계가 없으면 자식 측정 전에 실패하며 임의 기본 높이를 만들지 않습니다.

자식은 스크롤 축의 무제한 최댓값과 교차 축의 강제 크기로 측정합니다. 세로 스크롤은 실제 뷰포트 너비로 텍스트를 재배치합니다. 콘텐츠가 넘칠 때만 스크롤바 공간을 예약합니다. 제한된 측정 반복으로 두 축 스크롤바의 상호 의존을 해결하며, 수렴하지 않는 사용자 기하는 명시적으로 실패합니다. 0·아주 작은 할당에서는 음수 손잡이 기하를 만들지 않고 클립합니다.

`Offset`은 유한·음이 아닌 요청 오프셋입니다. 순수 측정에서는 바꾸지 않고 렌더 시 현재 콘텐츠 범위로 축별 제한합니다. 휠은 중첩 자식 다음에 처리하므로 가장 가까운 이동 가능한 뷰포트가 축별 소유권을 얻고, 경계의 안쪽 뷰는 바깥에 전달합니다. 변경은 다음 프레임을 요청합니다. 기존 자식 커널처럼 그리기 후 처리한 이벤트는 그 다음 프레임에 보입니다.

`UiScrollOptions.RightToLeft = true`이면 가로로 넘치는 콘텐츠가 오른쪽 끝에서 시작합니다. `Offset.X`가 커질수록 왼쪽 콘텐츠가 표시되고, 세로 스크롤바는 왼쪽에 놓입니다. 휠과 손잡이는 화면 좌표를 기준으로 움직이며 세로 오프셋은 위쪽부터 계산합니다. 샘플의 `Direction` 버튼으로 양축 뷰의 방향을 바꿀 수 있습니다.

기존 `UiRetainedLayout` 페이로드는 할당된 자식을 위한 준비 기하를 보관하며, 프레임 간 측정 재사용은 조건부입니다. 자식/속성 무효화, 제약, 타이포그래피/리소스 키와 스크롤바 두께로 재사용을 판단합니다. 휠 이동은 측정을 무효화하지 않습니다. 유지하지 않는 콘텐츠는 새로 측정합니다. 런타임 테마 레지스트리·별도 렌더러·전역 스크롤 소유자 레지스트리는 추가하지 않습니다.

## Windows 접근성

Windows UI Automation은 뷰를 Pane으로 노출하고 접근성 트리에서 콘텐츠를 그 아래에 배치합니다. `AccessibleName`으로 뷰포트의 이름을 지정합니다. 화면에 보이는 뷰포트에 콘텐츠가 넘치면 Pane에서 해당 축의 Scroll 패턴을 제공합니다. 백분율 및 단계 이동 요청은 자식 렌더링 전에 오프셋에 적용되므로 자식의 경계와 가시성이 같은 프레임에 반영됩니다. 콘텐츠가 뷰포트에 들어오면 Scroll 패턴이 사라지고 Pane과 자식 계층은 유지됩니다.

스크롤 가능한 뷰 안의 접근성 요소는 화면 밖에서도 ScrollItem 패턴을 제공합니다. `ScrollIntoView`는 잘리기 전의 배치 경계를 사용해 가장 안쪽 뷰포트부터 바깥으로 이동량을 계산합니다. 같은 요소가 표시된 프레임이 접근성 트리에 게시된 뒤 요청을 완료하며 키보드 포커스는 유지합니다. 요소가 사라지거나 별도 클립 때문에 표시할 수 없으면 요청이 실패할 수 있습니다.

Windows UI Automation은 유지 중인 Pane의 양축 스크롤 위치·뷰포트 비율·스크롤 가능 여부와 Scroll 패턴 제공 여부가 바뀌면 알립니다. 클라이언트는 알림을 받는 즉시 같은 Pane에서 새 값을 읽을 수 있습니다. 스크롤할 수 없게 된 축의 위치는 `-1`, 뷰포트 비율은 `100`입니다. 값이 바뀌지 않은 속성은 알림을 보내지 않습니다. 스크롤 가능한 Tooltip도 같은 게시 경로를 사용합니다.

RTL에서는 가로 UIA 백분율의 `0`이 오른쪽, `100`이 왼쪽입니다. 가로 증가 명령은 뷰포트를 왼쪽으로 이동합니다. `ScrollIntoView`는 중첩 뷰포트의 실제 화면 클립을 기준으로 동작합니다. [Microsoft Scroll 패턴](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-implementingscroll)

유지 중인 Pane과 렌더링되는 접근성 자식은 배치 또는 클립 변경에 따라 `BoundingRectangle`과 `IsOffscreen` 알림을 보냅니다. 사각형은 공급자가 노출하는 클립된 화면 좌표와 일치합니다. 직접 자식의 추가·제거·부모 이동·순서 변경이 있으면 유지 중인 Pane이 해당 프레임에 `ChildrenInvalidated`를 한 번 보냅니다. 클라이언트는 즉시 새 목록을 탐색할 수 있습니다. 스크롤로 유지 중인 자식의 가시성만 바뀌면 목록은 그대로입니다. [Microsoft Pane 컨트롤 형식](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-supportpanecontroltype)

## 좌표 정밀도와 남은 작업

현재 구현은 자식 전체를 월드 좌표로 렌더합니다. 큰 목록의 가상화나 좌표 재배치는 구현하지 않았습니다. 100만 단위 검사는 높이 60의 뷰포트 전체를 유지합니다. 10억 단위 검사에서는 float 상쇄로 보이는 클립이 줄어드는 결함을 확인했습니다. 이제 일반 뷰포트 연산의 반올림만 허용하고, 표현할 수 없는 배치는 자식 렌더/입력 전에 `NotSupportedException`으로 거부합니다. 이전 실패 로그와 가드 이전 소스를 보존했습니다. 명시적 미지원이며 10억 단위 렌더 성공이 아닙니다.

큰 콘텐츠 좌표 재배치, 보이는 항목 생성, 항목 재사용과 전체 가상화 수명은 남은 필수 작업입니다. 컨테이너 원장은 3/6을 유지하며 전체 목표도 active입니다.

## 근거와 샘플

`artifacts/scroll-view-uia-2026-11-11/verification.json`에는 ScrollView CPU 검사 52개와 별도 Windows UI Automation 클라이언트의 샘플 조작 결과가 있습니다. 클라이언트는 Pane 아래의 편집기를 찾아 화면 밖으로 이동한 뒤 같은 요소를 다시 표시했고, 두 축의 위치를 독립적으로 지정했습니다.

샘플의 `Toggle row`는 행이 차지하는 공간을 유지하면서 접근성 자식 하나를 추가하거나 제거합니다. 별도 UIA 클라이언트로 두 목록 변경 알림, 편집기의 가시성 알림, 뷰포트 너비 변경 뒤의 화면 사각형을 확인합니다.

`artifacts/scroll-view-2026-11-10/verification.json`에 고정 .NET11 RC3 근거를 기록합니다. 소유 뷰 CPU 47검사가 순수 측정, 축/공간 예약, 유지/무효화/스타일 변경, 중첩 휠, 실제 편집기의 입력/undo/Core 접근성, 해제, 컨텍스트 이동, 예외와 표현 가능성을 통과했습니다. 별도 확대 좌표 회귀는 1,933검사이며 새 오프셋 144검사·실제 취득 이미지 144비교를 포함합니다. readback 1,313회, 래스터/벡터·MSAA 1/4·Light/Dark·프레임 슬롯 3입니다. 중복 범위를 고유 요구사항 수나 성능 개선으로 해석하지 않습니다. 빌드 경고·오류는 0개입니다.

`samples/fba/layout_scroll_view_fba.cs`는 이름이 지정된 세로/양축 뷰, 실제 편집기, 클릭 행, Width/Height와 Top/End를 보여 줍니다. 지원 셸에서는 `./run-fba.ps1 samples/fba/layout_scroll_view_fba.cs -NoCache`를 우선합니다. 저장된 스모크는 기존 PS5 실행기 한계 때문에 본문이 같은 로컬 프로젝트 사본을 사용합니다. 현재 Native/런타임 비교와 공식 외형은 미검증입니다. 사용자 리사이즈 보류와 전체 목표 끝의 .NET9/10 배포 컴파일도 유지합니다.

## 콜백 중 준비한 배치 사용

앞쪽 컨트롤이 현재 프레임의 부모 측정 이후 뒤쪽 형제를 바꿀 수 있습니다. 최초 샘플에서 이미 할당한384에 새 자식624를 넣으려는 가로 초과를 관찰했고, 결정적 CPU 콜백으로 재현했습니다. 이제 측정 재사용과 준비한 자식 경계의 사용을 구분합니다. 정확한 부모 할당은 준비한 기하를 사용하고, 무효화 후 다음 부모 측정이 새로 계산합니다. 글리프 관찰자는 프레임 간 측정 재사용을 계속 끄지만 비유지 레이아웃도 현재 할당 렌더를 위한 프레임 번호가 있는 배치를 보관합니다. Row/Column·단일 자식 상자·Stack·Wrap/Grid·ScrollView가 이를 공유합니다. 자식 소스 값이나 자식 배열을 복제하지 않습니다.

기존 페이로드에 프레임 정수 하나가 추가되며, 비유지 컨테이너도 최초 배치 준비 시 한 번 획득합니다. 비유지 경로의 첫 획득 비용은 남은 성능 위험이며 최적화라고 보고하지 않습니다. 제한된 관리10,000-Padding 진단 한 쌍에서는 생성5,280,384B·첫 배치2,320,000B·정상 유지0B·무효화 재사용0B가 같았습니다. 모든 페이로드 형식이나 관찰자 경로의 획득을 측정한 것이 아니며 전체 앱 벤치도 아닙니다.

샘플의 선택적 `DUXEL_SAMPLE_EXERCISE=1` 구동기는 트리 렌더 도중 Width/Height·Top/End를 바꾸어 실제 콜백 순서를 재현합니다. 최종 정상/디스크 폰트 캐시 비활성 실행으로 이를 검사하며 수동 OS 입력을 대체하지 않습니다. 최초 창 실행 실패와 CPU 수정 전 결과는 근거 폴더에 남깁니다. 앱 프로세스는 관리 .NET11이며 NativeAOT는 미검증입니다.
새 샘플에는 현재 로컬 소스가 필요하며, 이전 배포 패키지가 새 팩터리의 지원 근거는 아닙니다.
