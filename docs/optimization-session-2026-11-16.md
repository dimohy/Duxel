# 행 위치 연결의 비용 진단

## 공통 입력/표시 단계 적용

논리 이벤트를 모두 유지하면서 중간 표시 생성을 생략하는 공통 단계를 구현했습니다. 컨텍스트·제어·연결된 빌더가 같은 `UiRenderPhase`를 읽고, 마지막 단계만 그리기 데이터를 만듭니다. 화면·배치·입력·접근성은 계속 순회합니다. 텍스트 래스터와 원시 기하 생성을 중간 단계에서 생략하고 레이어·순수 페인트 그룹에 빈 캐시가 들어가지 않게 했습니다. 자원 명령은 최종 소비자까지 보존하고 표시끼리 갱신 이력을 비교합니다. 옵저버 FPS도 표시 단계만 집계합니다.

새 계획으로254 기준과264 후보를 독립6회 `A1/B1/B2/A2/A3/B3` 순서로 비교했습니다. 기존 합성 글리프·Core 전용 진단의 입력1/8/32개×버튼0/64개, 워밍업8·측정24프레임을 그대로 사용했습니다. 텍스트와 콜백·입력 개수는 동일했고 후보는 단계 수에 관계없이 그리기1개였습니다. 64버튼·32입력의 실행별 평균은11.16~11.57ms에서7.34~8.70ms로 감소했습니다. 반면8입력은 후보1.62~2.54ms와 기준2.08~2.30ms가 겹치고 후보 한 회가 더 느려 개선으로 확정하지 않습니다. 단일 입력도 변동 범위가 겹칩니다. 평균 변화율·할당량·모든 원시 실행은 [대조 기록](../artifacts/goal-audit-2026-11-16/presentation-phase-cost-verification.json)에 보존합니다.

265 최종 코드는 입력 단계에서도 명시된 잘못된 그리기 인수를 거부하도록 검증 순서를 유지하고15개 검사를 추가했습니다. 시간 측정은264 이미지의 기록이며 예산을 늘려 재측정하지 않았습니다. 현재 제품·OS 글꼴·네이티브 입력·Linux 지연 또는 고정 RC3 NativeAOT 성능 수용으로 확대하지 않습니다. 구간 분리가 임의 화면 코드나 배치 자체를 제거한 것도 아닙니다. 회귀·최종 픽셀 비교와 남은 변환/플랫폼 수용 범위는 [공통 단계 계약](input-event-batches.ko.md#입력과-표시-단계)에서 구분합니다.

## 입력 묶음 CPU 구간 진단

가설은 중간 그리기 결과를 매번 마무리하는 비용이 큰지, UI 구성 자체가 큰지 구분하는 것입니다. 공통 `UiContext`에 옵션형 `UiInputProcessingMetrics`를 연결하고 준비·UI 구성·그리기 마무리·전체 시간과 렌더 스레드 할당을 기록했습니다. 기본은 꺼짐이고 옵저버의 스냅샷 버튼으로만 결과 문구가 바뀝니다. 실패 호출은 완료한 부분 개수를 남깁니다. 별도 실행기는 만들지 않고 기존 관리 검사 프로그램에 고정 진단을 추가했습니다.

247 진단은 입력1/8/32개×고정 버튼0/64개의6조건, 워밍업8프레임·측정24프레임을 독립3회 실행했습니다. 정확한 최종 입력과 이벤트마다 실행되는 콜백 수가 모두 맞았습니다. 64버튼·32입력의 실행별 평균은 전체11.73~12.08ms, UI 구성11.08~11.39ms, 마무리0.29~0.31ms였습니다. 렌더 스레드 할당의 평균은 약435KB였습니다. 32개 논리 단계에서 그리기 구성도32회입니다. 원시 구간별 수치는 `W:/Cache/Duxel/input-cpu-20261116/cpu247-1/result.json`부터3개 파일에 보존했습니다.

## 키 반복 담당 주체 분리

운영체제가 반복을 전달하는 동안 엔진 타이머도 살아 있어 입력 없는 프레임에서 커서 이동과 반복 질의를 추가하는 문제를 재현했습니다. 선택 속성만 추가한 235 기준은 129개 중 19개가 실패했습니다. `UiKeyRepeatSettings.Source`와 공통 `UiState.KeyRepeatSource`로 담당을 정하고 Windows 시스템 설정은 플랫폼 방식을 선택하게 했습니다. 플랫폼 방식은 전달된 입력을 그대로 처리하고 엔진 키 타이머를 만들지 않습니다. 수동 호스트는 기존 엔진 방식을 유지하며 일반 키 질의도 첫 누름에서 지연을 시작하도록 수정했습니다.

수정 후 같은 129개가 통과했습니다. 세 편집기·질의·키 해제·주체 전환·유효성·Windows 기본값을 확인했으며 플랫폼 방식의 유휴 프레임이 추가 커서 이동을 만들지 않음을 검증했습니다. 전환 때 이전 키 타이머를 폐기하고 경쟁 타이머는 오류로 알립니다. 마우스 스핀 반복과 애니메이션은 독립적으로 유지합니다. 불필요한 입력 동작과 타이머를 제거한 정확성 검증이며 전체 CPU 시간·FPS 개선율을 측정한 결과는 아닙니다. 일반 입력 전용 처리와 전체 포커스·수명·Linux 실행 검증은 남아 있습니다. ## 입력 이벤트 시계 분리

가설: 같은 호스트 프레임에 모인 이벤트가 프레임 시각 하나를 공유해 클릭 간격·키 반복 의미를 잃습니다. 입력 시각 속성만 추가한 221 기준 검사 84개 중 8개가 실패했습니다. `EventTimeSeconds`를 실제 Core 소비 경로에 연결하고 입력 시계를 애니메이션 시계와 분리했습니다. 처음 84개 통과 뒤 편집기·반복 질의·유휴 검사를 4개 추가해 88개 중 첫 누름 처리 2개 실패를 더 재현했습니다. 한 줄 입력과 반복 질의의 타이머 시작도 공통으로 수정해 최종 88개가 통과했습니다.

## 제거한 입력의 IME 수명

입력창을 폐기해도 Windows IME가 조합 대상·문자 대상·대기 확정 큐를 유지하는 결함을 재현했습니다. 수정 전 순서 검사 218개 중 24개가 실패했습니다. 필수 `IUiImeHandler.ReleaseInput` 계약을 공통 텍스트 소유자 해제에 연결하고 Windows에서 해당 id의 큐와 대상·커서 위치를 해제했습니다. 살아 있는 숨김 입력은 해제하지 않습니다. 조합 취소는 HWND 소유 스레드에 요청하며 대상 없는 UTF-16 후속 단위는 새 포커스로 넘기지 않습니다. 폐기 id 목록을 쌓지 않아 같은 id를 새로 사용할 수 있습니다.

수정 후 동일 218개와 저수준 IME 323개가 통과했습니다. 후자는 기존 313개에 재사용·다른 큐 보존·직접 취소 검사 10개를 더했습니다. 이는 소유권·큐 수명 정확성 검사이며 전체 힙 사용량·CPU 시간·FPS 감소율을 측정한 결과는 아닙니다. 사용자 정의 IME 처리기는 새 필수 메서드를 구현해야 합니다.
